### Environment gotchas found in practice (2026-09-13, 2026-09-14)

- **`pcbnew` imports only under `/usr/bin/python3`.** `python3` is mise-shimmed and cannot see it. The project venv is created with `--system-site-packages` from the system interpreter for this reason.
- **KiCad 10.0.6's own `pcbnew.py` is broken on Python 3.14.** Container `__iter__` methods call `it.next()`, a Python-2 idiom, while this SWIG build exposes only `__next__`. Any `GetTracks()` / `GetDrawings()` / `GetFootprints()` iteration raises `AttributeError`. `hardware/kicad_compat.py` patches it; import that before `pcbnew` in every script.
- **kbplacer needs the `[schematic]` extra** (`kicad-skip`) or `--create-sch-file` fails with "Requires optional schematic dependencies".
- **kbplacer takes absolute `.pretty` paths**, not library nicknames, so no fp-lib-table registration is needed *to run it* — but the board it writes references the library by bare nickname (`marbastlib-mx`), and that nickname has to resolve afterwards or every switch footprint reports `lib_footprint_issues` in DRC and `footprint_link_issues` in ERC. Corrected 2026-09-14: PCM **did** register marbastlib globally, under the prefixed nicknames `PCM_marbastlib-mx`, `PCM_marbastlib-xp-mx` and so on in `~/.config/kicad/10.0/fp-lib-table` — so this was never a missing library, only a nickname mismatch. Fixed by giving each main project its own `fp-lib-table` mapping the bare `marbastlib-mx` to `${KICAD10_3RD_PARTY}/footprints/com_github_ebastler_marbastlib/marbastlib-mx.pretty`, matching the global table's own path convention so the entry stays portable. That cleared 140 warnings across the two main boards.
- **Width templates must match the library's own spelling.** marbastlib names widths `1u`, `1.25u`; a plain `{}` renders 1.0 as `1.0u` and fails to load. Use `{:g}`.
- **`--additional-elements` REPLACES the default** rather than adding to it. Omitting `ST{}` silently leaves stabilizers stranded at the origin.
- **`--create-led-pcb-elements` does not position anything.** It creates and nets the LEDs and capacitors but leaves every one stacked at (0,0) unless they are also named in `--additional-elements`.
- **marbastlib hotswap switch footprints must be placed on the BACK.** Their socket pads are on `F.Cu` and the pin holes are drawn mirrored, i.e. the footprint is drawn as seen from underneath. Placed on the front (kbplacer's default) the socket ends up on the same side as the switch. Pass `-s "SW{} 0 BACK"`. Verify by the pin1->pin2 vector, which must be `(-6.35, 2.54)` to match KiCad's stock `SW_Cherry_MX_1.00u_PCB` — absolute pad coordinates are not comparable between libraries because the origins differ (marbastlib uses the switch centre, KiCad stock uses pin 1).
- **Switch orientation must be checked against the centre post, not the pin vector.** A 180 deg rotation with swapped pin numbering leaves the pin1->pin2 vector unchanged, so that test passes on a board that is rotated wrong. KiCad's stock `SW_Cherry_MX_1.00u_PCB` puts pins NORTH of the switch centre: `(+2.54,-5.08)` and `(-3.81,-2.54)`. Compare absolute positions relative to the centre-post NPTH.
- **`--additional-elements` / `-d` offsets are in the switch's ROTATED frame.** With `SW{} 180 BACK`, an offset of `+5.08` lands at `-5.08` on the board. Invert the signs.
- **kbplacer leaves duplicate-numbered pads unnetted.** marbastlib's hotswap footprint has pad "1" three times (one PTH, two SMD); only one gets a net, and DRC then reports the switch shorting itself. `generate_main_pcbs.py` post-processes this.
- **Saving a board rewrites its project file.** Any `.kicad_pro` rule change must be applied *after* the last `board.Save()`, or it is silently reverted.
- **`GetBoardEdgesBoundingBox()` counts footprint-internal `Edge.Cuts`.** The reverse-mount SK6812MINI-E footprint cuts its own hole, so 640 of them inflate the reported board size. Measure the outline from board-level drawings only.
- **A KiCad 6 schematic keeps per-instance value and footprint in the sheet-level `symbol_instances` block**, not in each symbol's own property fields, which sit empty. Anything reading symbol properties — Konnect's `bom_health` audit included — then reports those parts as having no value and no footprint. `dyad-controller.kicad_sch` was `version 20211123`, inherited wholesale from `upstream/RP2040-Guide.kicad_sch` (same sheet UUID), and R2 looked valueless for exactly this reason while `symbol_instances` carried `1k` all along. The same gap blocks writes: Konnect refuses `add_schematic_component` with `stale_target`, because there are no per-symbol `(instances)` blocks for it to preserve. **`kicad-cli sch upgrade` does not fix it** — it converts the format but *drops* the instance data instead of migrating it. The only thing that works is opening the schematic in KiCad once and saving; that also writes the project name and real sheet UUID into `.kicad_pro`, which were empty and all-zeros. Upgrade before trusting any BOM or library audit on a vendored schematic. Checked across the repo 2026-09-14: only the controller was affected. Both main PCBs are `version 20250114` with per-symbol instances intact (65/65, 74/74, plus the LED-chain sheets), so they need no upgrade — though their schematics report generator `9.0` against boards at `10.0`, which is why `get_project_info` returns a null compatibility `kicad_version` for them.
- **Konnect's live-IPC tools split on whether they call `GetOpenDocuments`, which KiCad 10 does not implement.** `query_traces` uses it as a board-identity pre-check, so it fails *permanently* on this build with `KiCad IPC error: no handler available for request of type kiapi.common.commands.GetOpenDocuments (AS_UNHANDLED)` — even with the board open and IPC perfectly healthy. The tell is `AS_UNHANDLED` rather than a connection error: at the same moment `check_kicad_ui` reports `ipc_responsive: true` and `get_nets_list` reads all 91 nets off the live board. Tools that take a UUID or raw coordinates instead (`modify_trace`, `route_trace`) work fine, which is how the COL6 clearance fix was applied. Do not read the failure as "the board is not open", and do not fall back to editing the `.kicad_pcb` behind a running KiCad — Konnect's own PreToolUse guard forbids it. Note also that IPC edits live in KiCad's memory only: the file on disk is unchanged until you save in the GUI, so verify with `kicad-cli` *after* Ctrl+S, not before.
- **kbplacer bundles multi-sheet projects `flat` on KiCad 10**, tying the sheets together only through the `sheets` list in `.kicad_pro` rather than with hierarchical sheet symbols — so a root `.kicad_sch` with zero `(sheet` blocks is correct here, not broken. The catch is that the tooling around it disagrees: `kicad-cli pcb drc --schematic-parity` reads a single `.kicad_sch` and reports every *other* sheet's footprints as `Extra footprint` (64 phantom findings on main-left, 74 on main-right), and Konnect's `--schematic-scope hierarchy` audits follow hierarchical sheet symbols, of which a flat project has none, so `check_bom_health` counted 65 of ~195 components. Verify the real structure by matching each `.kicad_sch`'s own `(uuid …)` against the `.kicad_pro` `sheets` entries before believing an orphan report. `generate_main_pcbs.py` now passes `--bundle-strategy hierarchical` to opt out, so those checks mean something; the cost is diverging from kbplacer's KiCad 10 default.
- **marbastlib's hotswap switch footprints stop at 1.75u**, so kbplacer falls back to 1.0u for anything wider and logs `Requested width 2.25u not available for SW_MX_HS_CPG151101S11, using 1.0u fallback`. That warning is harmless. Diffing `SW_MX_HS_CPG151101S11_1u` against `_1.75u` leaves exactly one substantive difference: the keycap rectangle on **`Dwgs.User`**, a documentation layer that is neither fabricated nor DRC-checked. Pads, drills, silkscreen, `F.Fab` and both courtyards are identical — the courtyard is a fixed +/-7 mm modelling the switch body, not the cap — so the fallback costs a drawing-layer outline and nothing electrical or mechanical. The part that does matter is correct: stabilisers go up to 10u, and the 2.25u key on the left half carries `STAB_MX_2.25u` centred on its switch. Measured 2026-09-14: D21 clears ST21's nearest hole by 1.53 mm.
- **kbplacer never links the board to the schematic**, so every footprint lands with an empty `(path)`. KiCad matches symbols to footprints by that path, so with it blank *Update PCB from Schematic* treats every symbol as new and re-adds the whole board — which makes any schematic-side edit impossible to push through. `generate_main_pcbs.py` now writes the link itself, in KiCad's format `<sheet path without the root uuid>/<symbol uuid>`; a root-level symbol on a flat sheet carries `/<symbol uuid>` alone. Beware when parsing these sheets: **kbplacer writes them unindented and KiCad rewrites them tab-indented on first save**, so a whitespace-keyed parser silently works on one and finds nothing in the other. Match brackets instead. Recovery note: `<project>/.history/` is a real git repo KiCad maintains, gitignored but fully usable — `git log` and `git show` in it recovered a hand-laid LED chain that a regeneration had overwritten, from its `SCH Save` commit.

## Case CAD

Parametric, driven by the same key-position data as the PCB (`hardware/layout/`), per PLAN.md §4/§6 Phase 4.

- **build123d** (pick) — Python, OCCT kernel (same as FreeCAD). Fillets/lofts/booleans handle the bearing race, ring-gear teeth (mechanism Option A, PLAN.md §2), and pod pockets much better than pure CSG.
- **FreeCAD** — same OCCT kernel, full GUI + sketcher + assembly workbench. Better for hand-iterating dimensions and consuming the STEP files KiCad exports (PLAN.md §3). Heavier than scripting alone; worth having installed regardless for STEP inspection.
- **OpenSCAD** — simplest scripting model, but CSG-only — the round bearing seat and ring-gear geometry get awkward without OCCT-style fillets. Probably not the pick here.

## Firmware (QMK)

- **QMK CLI** + **external userspace** — keymap lives outside the `qmk_firmware` tree, per PLAN.md §6 Phase 6.
- **Vial** (pick over VIA for this board) — the layout JSON compiles into firmware itself; no need to merge a keyboard definition into VIA's upstream repo or side-load unsigned JSON each session. Better fit while this board isn't upstreamed.
- **VIA** — reconsider only if the QMK keyboard definition actually gets upstreamed (PLAN.md §6 Phase 7 holds this as optional).
- **keymap-drawer** (+ `vial-to-keymap-drawer`) — renders the keymap for the build guide, Phase 7.

## Open questions

- GC9A01 breakout: no footprint in marbastlib (checked the library contents directly, not just the README). It's a generic round-LCD module with no standard KiCad library entry anywhere — plan to hand-draw a pin-header footprint once you've picked the exact module you're buying (pitch/pin-count vary by vendor).
- EC11 no-switch variant (EC11N — what PLAN.md §2 actually calls for, since the encoder's own click is deliberately unused): no footprint in either library, only an orphaned 3D model. Simplest path is probably to reuse the EC11E-Switch footprint body and just leave its switch pads unpopulated, rather than drawing a separate footprint — same mechanical part either way. Confirm that assumption once a specific supplier/datasheet is picked, since "E"/"N" suffixes aren't a reliably-documented standard across vendors.
- Pick one of the kicad-mcp implementations after a short hands-on trial (Seeed-Studio vs. mixelpixx vs. lamaalrajih) rather than committing from descriptions alone.
- Design the custom pod-placement script (kbplacer gap, above) before Phase 3 layout starts.
