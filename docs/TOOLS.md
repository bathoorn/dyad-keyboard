### Environment gotchas found in practice (2026-09-13, 2026-09-14)

- **`pcbnew` imports only under `/usr/bin/python3`.** `python3` is mise-shimmed and cannot see it. The project venv is created with `--system-site-packages` from the system interpreter for this reason. (2026-10-07: mise is not installed on the current machine and `python3` is the system interpreter, so the trap is dormant -- keep using `/usr/bin/python3` explicitly anyway.)
- **`requirements.txt` at the repo root pins the venv's contents** (kbplacer, kicad-skip, easyeda2kicad, sexpdata). `.venv-kicad/` is gitignored, so that file is the only record of what belongs in it. Recreate with `/usr/bin/python3 -m venv --system-site-packages .venv-kicad && .venv-kicad/bin/pip install -r requirements.txt` — the `--system-site-packages` flag is not optional, per the point above.
- **KiCad 10.0.6's own `pcbnew.py` is broken on Python 3.14.** Container `__iter__` methods call `it.next()`, a Python-2 idiom, while this SWIG build exposes only `__next__`. Any `GetTracks()` / `GetDrawings()` / `GetFootprints()` iteration raises `AttributeError`. `hardware/kicad_compat.py` patches it; import that before `pcbnew` in every script.
- **kbplacer needs the `[schematic]` extra** (`kicad-skip`) or `--create-sch-file` fails with "Requires optional schematic dependencies".
- **kbplacer takes absolute `.pretty` paths**, not library nicknames, so no fp-lib-table registration is needed *to run it* — but the board it writes references the library by bare nickname (`marbastlib-mx`), and that nickname has to resolve afterwards or every switch footprint reports `lib_footprint_issues` in DRC and `footprint_link_issues` in ERC. Corrected 2026-09-14: PCM **did** register marbastlib globally, under the prefixed nicknames `PCM_marbastlib-mx`, `PCM_marbastlib-xp-mx` and so on in `~/.config/kicad/10.0/fp-lib-table` — so this was never a missing library, only a nickname mismatch. Fixed by giving each main project its own `fp-lib-table` mapping the bare `marbastlib-mx` to `${KICAD10_3RD_PARTY}/footprints/com_github_ebastler_marbastlib/marbastlib-mx.pretty`, matching the global table's own path convention so the entry stays portable. That cleared 140 warnings across the two main boards.
- **Width templates must match the library's own spelling.** marbastlib names widths `1u`, `1.25u`; a plain `{}` renders 1.0 as `1.0u` and fails to load. Use `{:g}`.
- **`--additional-elements` REPLACES the default** rather than adding to it. Omitting `ST{}` silently leaves stabilizers stranded at the origin.
- **`--create-led-pcb-elements` does not position anything.** It creates and nets the LEDs and capacitors but leaves every one stacked at (0,0) unless they are also named in `--additional-elements`.
- **marbastlib hotswap switch footprints must be placed on the BACK.** Their socket pads are on `F.Cu` and the pin holes are drawn mirrored, i.e. the footprint is drawn as seen from underneath. Placed on the front (kbplacer's default) the socket ends up on the same side as the switch. Pass `-s "SW{} 0 BACK"`. Verify by the pin1->pin2 vector, which must be `(-6.35, 2.54)` to match KiCad's stock `SW_Cherry_MX_1.00u_PCB` — absolute pad coordinates are not comparable between libraries because the origins differ (marbastlib uses the switch centre, KiCad stock uses pin 1).
- **Switch orientation must be checked against the centre post, not the pin vector.** A 180 deg rotation with swapped pin numbering leaves the pin1->pin2 vector unchanged, so that test passes on a board that is rotated wrong. KiCad's stock `SW_Cherry_MX_1.00u_PCB` puts pins NORTH of the switch centre: `(+2.54,-5.08)` and `(-3.81,-2.54)`. Compare absolute positions relative to the centre-post NPTH.
- **`--additional-elements` / `-d` offsets are in the switch's ROTATED frame.** With `SW{} 180 BACK`, an offset of `+5.08` lands at `-5.08` on the board. Invert the signs.
- **kbplacer leaves duplicate-numbered pads unnetted.** marbastlib's hotswap footprint has pad "1" three times (one PTH, two SMD); only one gets a net, and DRC then reports the switch shorting itself. `generate_main_pcbs.py` post-processes this.
- **Saving a board rewrites its project file.** Any `.kicad_pro` rule change must be applied *after* the last `board.Save()`, or it is silently reverted.
- **`GetBoardEdgesBoundingBox()` counts footprint-internal `Edge.Cuts`.** The reverse-mount SK6812MINI-E footprint cuts its own hole, so 640 of them inflate the reported board size. Measure the outline from board-level drawings only.
- **A KiCad 6 schematic keeps per-instance value and footprint in the sheet-level `symbol_instances` block**, not in each symbol's own property fields, which sit empty. Anything reading symbol properties — Konnect's `bom_health` audit included — then reports those parts as having no value and no footprint. `dyad-controller.kicad_sch` was `version 20211123`, inherited wholesale from `upstream/RP2040-Guide.kicad_sch` (same sheet UUID), and R2 looked valueless for exactly this reason while `symbol_instances` carried `1k` all along. The same gap blocks writes: Konnect refuses `add_schematic_component` with `stale_target`, because there are no per-symbol `(instances)` blocks for it to preserve. **`kicad-cli sch upgrade` does not fix it** — it converts the format but *drops* the instance data instead of migrating it. The only thing that works is opening the schematic in KiCad once and saving; that also writes the project name and real sheet UUID into `.kicad_pro`, which were empty and all-zeros. Upgrade before trusting any BOM or library audit on a vendored schematic. Checked across the repo 2026-09-14: only the controller was affected. Both main PCBs are `version 20250114` with per-symbol instances intact (65/65, 74/74, plus the LED-chain sheets), so they need no upgrade — though their schematics report generator `9.0` against boards at `10.0`, which is why `get_project_info` returns a null compatibility `kicad_version` for them.
- **Konnect's live-IPC tools split on whether they call `GetOpenDocuments`, which KiCad 10 does not implement.** `query_traces` uses it as a board-identity pre-check, so it fails *permanently* on this build with `KiCad IPC error: no handler available for request of type kiapi.common.commands.GetOpenDocuments (AS_UNHANDLED)` — even with the board open and IPC perfectly healthy. The tell is `AS_UNHANDLED` rather than a connection error: at the same moment `check_kicad_ui` reports `ipc_responsive: true` and `get_nets_list` reads all 91 nets off the live board. Tools that take a UUID or raw coordinates instead (`modify_trace`, `route_trace`) work fine, which is how the COL6 clearance fix was applied. Do not read the failure as "the board is not open", and do not fall back to editing the `.kicad_pcb` behind a running KiCad — Konnect's own PreToolUse guard forbids it. Note also that IPC edits live in KiCad's memory only: the file on disk is unchanged until you save in the GUI, so verify with `kicad-cli` *after* Ctrl+S, not before. (2026-10-07: on Konnect 0.13.0, `open_project` listed the open board without error, so this may be fixed; `query_traces` was not retested.)
- **kbplacer bundles multi-sheet projects `flat` on KiCad 10**, tying the sheets together only through the `sheets` list in `.kicad_pro` rather than with hierarchical sheet symbols — so a root `.kicad_sch` with zero `(sheet` blocks is correct here, not broken. The catch is that the tooling around it disagrees: `kicad-cli pcb drc --schematic-parity` reads a single `.kicad_sch` and reports every *other* sheet's footprints as `Extra footprint` (64 phantom findings on main-left, 74 on main-right), and Konnect's `--schematic-scope hierarchy` audits follow hierarchical sheet symbols, of which a flat project has none, so `check_bom_health` counted 65 of ~195 components. Verify the real structure by matching each `.kicad_sch`'s own `(uuid …)` against the `.kicad_pro` `sheets` entries before believing an orphan report. `generate_main_pcbs.py` now passes `--bundle-strategy hierarchical` to opt out, so those checks mean something; the cost is diverging from kbplacer's KiCad 10 default.
- **marbastlib's hotswap switch footprints stop at 1.75u**, so kbplacer falls back to 1.0u for anything wider and logs `Requested width 2.25u not available for SW_MX_HS_CPG151101S11, using 1.0u fallback`. That warning is harmless. Diffing `SW_MX_HS_CPG151101S11_1u` against `_1.75u` leaves exactly one substantive difference: the keycap rectangle on **`Dwgs.User`**, a documentation layer that is neither fabricated nor DRC-checked. Pads, drills, silkscreen, `F.Fab` and both courtyards are identical — the courtyard is a fixed +/-7 mm modelling the switch body, not the cap — so the fallback costs a drawing-layer outline and nothing electrical or mechanical. The part that does matter is correct: stabilisers go up to 10u, and the 2.25u key on the left half carries `STAB_MX_2.25u` centred on its switch. Measured 2026-09-14: D21 clears ST21's nearest hole by 1.53 mm.
- **kbplacer never links the board to the schematic**, so every footprint lands with an empty `(path)`. KiCad matches symbols to footprints by that path, so with it blank *Update PCB from Schematic* treats every symbol as new and re-adds the whole board — which makes any schematic-side edit impossible to push through. `generate_main_pcbs.py` now writes the link itself, in KiCad's format `<sheet path without the root uuid>/<symbol uuid>`; a root-level symbol on a flat sheet carries `/<symbol uuid>` alone. Beware when parsing these sheets: **kbplacer writes them unindented and KiCad rewrites them tab-indented on first save**, so a whitespace-keyed parser silently works on one and finds nothing in the other. Match brackets instead. Recovery note: `<project>/.history/` is a real git repo KiCad maintains, gitignored but fully usable — `git log` and `git show` in it recovered a hand-laid LED chain that a regeneration had overwritten, from its `SCH Save` commit.
- **A root `.kicad_sch` whose own uuid disagrees with the project makes `kicad-cli --schematic-parity` useless.** `kicad-cli` resolves each footprint's `(path)` through the root sheet uuid; the KiCad GUI resolves through the project structure instead. When the two disagree the CLI cannot match a single footprint to its symbol and reports every pad on an unlabelled net as `net_conflict` / "No corresponding pin found in schematic" — 199 of them on main-right, covering every diode, every switch and LED1-LED26 — while the GUI sees nothing wrong and rewrites the board byte-identically. Three places must agree: the root `.kicad_sch`'s own `(uuid ...)`, the first component of every child sheet's symbol instance paths, and the Root entry in the `.kicad_pro` `sheets` list. Introduced here by restoring a root sheet from `.history` while the project had moved to a new root uuid. **Diagnostic:** compare against the other half. main-left has identical footprints, symbols and libraries and showed zero such findings, which ruled out the footprints long before the cause was found — reach for that control early when one board looks structurally wrong and the other does not.

### Controller layout and routing traps (2026-10-07)

Found while syncing, placing and routing the controller board. Grouped by tool.

**Setup**

- **A fresh machine is missing more than KiCad.** On top of the KiCad package itself: `kicad-library` and `kicad-library-3d` (stock footprints, symbols, 3D models -- the boards use `Capacitor_SMD`, `Diode_SMD`, `Connector_USB` and so on, and `generate_main_pcbs.py` reads `/usr/share/kicad/footprints` directly), marbastlib through PCM, the `.venv-kicad` venv, the `qmk` CLI plus `qmk setup`, a git identity, and Java for Freerouting. Install `qmk` with `pipx`, **not** into `.venv-kicad` -- it then only works with that venv activated and its dependencies fall outside `requirements.txt`.
- **Freerouting 2.4.1 needs Java 25 or newer.** On Java 21 it dies with `UnsupportedClassVersionError ... class file version 69.0`. On Arch, `jre-openjdk-headless` (the unversioned package) is current; make it the default with `sudo archlinux-java set java-<n>-openjdk`.
- **Konnect needs the KiCad API socket configured, not just enabled.** Enable *Preferences → Plugins → Enable KiCad API*, then put `ipc:///tmp/kicad/api.sock` into `ipc_socket_path` in the Konnect plugin's `settings.json`. A running Konnect server reads that file only at startup; its own `reload_server` tool picks it up without restarting the AI client.

**KiCad: closed or open**

- **Check for a running KiCad immediately before writing any board or project file, and stop if one is there.** Look for `~<name>.kicad_pcb.lck` beside the board. KiCad holds its own copy in memory and writes it back on save, silently undoing file-level edits -- and the project file is rewritten on every board save (see above), which also reverts netclass edits made to `.kicad_pro`. Read the check's result *before* the write, not in the same command.
- **File-based work therefore needs KiCad closed; live work goes through the API.** `kicad-python` (`pip install kicad-python`, imported as `kipy`) talks to the same socket as Konnect and does bulk edits in one undo step (`begin_commit` / `push_commit`), which Konnect's one-item tools cannot -- e.g. deleting 465 tracks and vias at once. `board.revert()` reloads the board from disk, and `board.save()` saves.
- **`kipy`: never update the same footprint twice inside one commit.** It produced a *second* copy of each such footprint with the *same* KIID -- one moved, one left behind -- and saving wrote both to the file. Same-ID duplicates cannot be removed by ID; the only recovery was restoring the board from git and reloading. Set position and rotation in a single `update_items` call per footprint.
- **A footprint's position is its origin, which is not always its centre.** A pin header's origin is pin 1, so "centring" a 1x05 at a point put pin 5 past the board edge. Place from pad positions, not from the origin.

**Konnect**

- **`update_pcb_from_schematic` treats bare pads as routed copper.** It refused three pad net changes (`routed_pad_net_change`) on a board with no tracks at all, because it reads routing from the *saved* file rather than the live board. Saving did not help; pre-assigning the three pad nets live, to exactly what the sync would set, did.
- **`update_pcb_from_schematic` does not swap footprints that changed in the schematic.** A footprint whose library ID changed is either a `footprint_id_changed` conflict or, as with SW1 (pin header → tactile switch), silently left as the old part. It also never deletes board-only footprints. Use KiCad's own *Update PCB from Schematic* with "replace footprints" for those.
- **`place_component` drops the library footprint's attributes.** Mounting holes placed with it lost `exclude_from_bom` and `exclude_from_pos_files` and would have gone onto the JLCPCB BOM as parts. Re-check attributes after placing.
- **`export_specctra_dsn` accepts only front-side parts and a straight-line outline.** The controller has every part on B.Cu and rounded corners, so it is out. Use KiCad's own `pcbnew.ExportSpecctraDSN(board, path)` and `pcbnew.ImportSpecctraSES(board, path)` on the file, with KiCad closed.

**KiCad itself**

- **The stock USB-C symbol and footprint disagree on the shield pin.** `Connector:USB_C_Receptacle_USB2.0` names it `S1`; KiCad 10's `USB_C_Receptacle_HRO_TYPE-C-31-M-12` names the four shell pads `SH`. A KiCad 6 copy of the footprint still says `S1`, which hides the mismatch until a fresh one is placed. Fixed with `dyad:USB_C_Receptacle_HRO_TYPE-C-31-M-12`, shell pads renumbered `S1`.
- **Change Footprint nets only one pad of each duplicate-numbered pair.** The TS-1187A button has pads 1,1,2,2; after the swap two of the four had no net. It also carried the old part's value and BOM exclusion over. Same family as kbplacer's duplicate-pad trap above.
- **`min_copper_edge_clearance` defaulted to 0** in the controller project, so DRC never flagged a pad hanging off the board. It is now 0.3 mm. Check this setting on any new or vendored project.
- **Thermal-relief spokes do not fit on fine-pitch GND pads.** DRC reports `starved_thermal` on the RP2040 exposed pad, 0.5 mm-pitch FFC GND pins, SOIC GND and USB-C shell pads. These are already connected by tracks; give those pads a solid zone connection (`pad.SetLocalZoneConnection(ZONE_CONNECTION_FULL)`) -- for the QFN exposed pad that is the right choice anyway.
- **`pcbnew` from Python is fragile for bulk edits.** Removing all tracks from a loaded board in a loop crashed the interpreter before it saved; on a scratch copy it was simpler to strip the top-level `(segment` / `(via` / `(zone` blocks by bracket matching. A freshly created `ZONE` also reported the wrong layer through `GetLayerName()` -- trust the saved file. And `PCB_TRACK` objects are unhashable: key sets on `m_Uuid.AsString()`.

**Freerouting**

- **The optimizer can take longer than the routing, and the output is written only at the very end.** On the controller, routing took ~5 minutes and one optimizer pass 14; a 25-minute timeout then killed the run and saved nothing. Pass `--router.optimizer.enabled=false` and tidy by hand in KiCad. Headless: `java -jar freerouting-2.4.1.jar -de in.dsn -do out.ses -mp 100 --gui.enabled=false`.
- **Per-layer costs go in an `(autoroute_settings ...)` block inside the DSN's `(structure ...)`, after both `(layer ...)` definitions.** Placed before them, Freerouting reports "layer not found" and crashes with a `NullPointerException`. Syntax: `(layer_rule F.Cu (active on) (preferred_direction vertical) (preferred_direction_trace_costs 4.0) (against_preferred_direction_trace_costs 6.0))`, plus `(via_costs n)`. The command line has no per-layer option.
- **Freerouting ignores KiCad's hole-to-hole rule and its custom `.kicad_dru` rules, and necks tracks down where it is tight.** Expect 6-24 vias 0.44-0.496 mm apart against a 0.5 mm rule, tracks at 0.15 mm, and clearance misses at fine-pitch connectors after every run. Fix vias with a search for the smallest move that clears every hole and all other-net copper on both layers (moving straight away from the neighbour pushed five vias into tracks).
- **Do not rerun Freerouting to finish one unrouted net.** On an already-routed DSN its fanout stage tore up existing routing: it started from 40 unrouted nets and ended at 14. Rerun the whole board with a different strategy instead -- `-is random` routed 100% where the default order left one net.
- **Layer costs move copper between layers more than they improve the board.** Making F.Cu 4x-15x as expensive mostly swapped which layer kept a continuous GND fill. Measure what matters -- the share of each fast net's length with GND fill on the opposite layer -- rather than whole-board coverage. On the controller, moving the flash next to the RP2040 halved the QSPI wiring, which no cost setting achieved.

## Case CAD

Parametric, driven by the same key-position data as the PCB (`hardware/layout/`), per PLAN.md §4/§6 Phase 4.

- **build123d** (pick) — Python, OCCT kernel (same as FreeCAD). Fillets/lofts/booleans handle the bearing race, ring-gear teeth (mechanism Option A, PLAN.md §2), and pod pockets much better than pure CSG.
- **FreeCAD** — same OCCT kernel, full GUI + sketcher + assembly workbench. Better for hand-iterating dimensions and consuming the STEP files KiCad exports (PLAN.md §3). Heavier than scripting alone; worth having installed regardless for STEP inspection.
- **OpenSCAD** — simplest scripting model, but CSG-only — the round bearing seat and ring-gear geometry get awkward without OCCT-style fillets. Probably not the pick here.

## Firmware (QMK)

- **QMK CLI** + **external userspace** — keymap lives outside the `qmk_firmware` tree, per PLAN.md §6 Phase 6.
- **Vial** (pick over VIA for this board) — the layout JSON compiles into firmware itself; no need to merge a keyboard definition into VIA's upstream repo or side-load unsigned JSON each session. Better fit while this board isn't upstreamed.
- **VIA** — reconsider only if the QMK keyboard definition actually gets upstreamed (PLAN.md §6 Phase 7 holds this as optional).
- **keymap-drawer** (+ `vial-to-keymap-drawer`) — renders the keymap for the build guide, Phase 7.

## Open questions

- GC9A01 breakout: no footprint in marbastlib (checked the library contents directly, not just the README). It's a generic round-LCD module with no standard KiCad library entry anywhere — plan to hand-draw a pin-header footprint once you've picked the exact module you're buying (pitch/pin-count vary by vendor).
- EC11 no-switch variant (EC11N — what PLAN.md §2 actually calls for, since the encoder's own click is deliberately unused): no footprint in either library, only an orphaned 3D model. Simplest path is probably to reuse the EC11E-Switch footprint body and just leave its switch pads unpopulated, rather than drawing a separate footprint — same mechanical part either way. Confirm that assumption once a specific supplier/datasheet is picked, since "E"/"N" suffixes aren't a reliably-documented standard across vendors.
- Pick one of the kicad-mcp implementations after a short hands-on trial (Seeed-Studio vs. mixelpixx vs. lamaalrajih) rather than committing from descriptions alone.
- Design the custom pod-placement script (kbplacer gap, above) before Phase 3 layout starts.
